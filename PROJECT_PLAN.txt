SILICON SWITCH LAB: IMPLEMENTATION AND INTERVIEW ROADMAP
=======================================================

1. PROJECT OUTCOME
==================

Build a cross-platform, hardware-inspired network switch/router in C++17 with:

- Ethernet frame parsing and serialization
- Virtual ports and 802.1Q VLAN membership
- MAC learning, known-unicast forwarding, and unknown-unicast flooding
- ARP/neighbor state
- IPv4 forwarding with TTL handling and longest-prefix matching
- Next-hop and ECMP groups
- ACL-style match/action rules
- Bounded ingress/egress queues, counters, and explicit congestion drops
- A SAI-inspired control API
- Desired-state and observed-state reconciliation
- Python configuration, test, and traffic tools
- Deterministic simulation plus a distributed UDP transport
- Unit, integration, concurrency, fault-injection, and benchmark suites

This is an educational project, not a production switch and not an
implementation of any vendor's proprietary technology.

3. ARCHITECTURE
===============

3.1 Data plane
--------------

Packet enters virtual port
  -> validate frame length
  -> parse Ethernet and optional VLAN header
  -> determine ingress VLAN
  -> learn source MAC
  -> apply ingress ACL
  -> bridge lookup or IPv4 route lookup
  -> select egress port/next hop
  -> rewrite required headers
  -> enqueue in bounded egress queue
  -> schedule and transmit
  -> update stage-specific counters

Core C++ types:

- MacAddress, Ipv4Address, Ipv4Prefix
- EthernetFrame, ArpPacket, Ipv4Packet
- PortId, VlanId, RouteId, NextHopId
- MacTable, NeighborTable, RouteTable, AclTable
- BoundedQueue<T>, VirtualPort, PacketPipeline
- HardwareInterface, SoftwareAsic

Important invariants:

- Packet reads never exceed available bytes.
- Multi-byte wire values have explicit byte-order conversion.
- Every table has an explicit capacity.
- A route prefix is normalized when created.
- No hardware operation silently partially succeeds.
- Queue drops identify a reason and increment the matching counter.
- The control plane does not hold its state lock across a slow hardware call.

3.2 Control plane
-----------------

The control plane holds desired state. A SAI-inspired interface maps portable
objects to the HardwareInterface. A reconciliation loop compares desired state
with observed hardware state after restart, injected failure, or drift.

Operations:

- create/remove port
- create/remove VLAN and VLAN membership
- create/update/remove route
- create/update/remove next hop and neighbor
- create/remove ACL rule
- read counters and resource usage
- dump desired and observed state
- reconcile

Every mutation defines:

- input validation
- idempotency behavior
- dependency behavior
- resource-exhaustion behavior
- completion/error result
- rollback or forward-reconciliation behavior

3.3 Python layer
----------------

Python tools will:

- load a topology from JSON
- configure ports, VLANs, routes, and ACLs
- generate deterministic traffic scenarios
- poll counters with deadlines
- compare expected and observed hardware state
- collect logs from multiple computers
- output machine-readable test reports
- run performance experiments

3.4 Distributed transport
-------------------------

Each virtual port can connect to a UDP endpoint. A small envelope carries:

- protocol version
- switch/port identity
- sequence number
- payload length
- checksum
- serialized Ethernet frame

UDP is transport for the lab, not a replacement for the simulated Ethernet
behavior. The envelope is removed before the frame enters the data plane.


4. FOUR-COMPUTER LAB
====================

Recommended initial topology:

Linux desktop
  - Runs the SoftwareAsic process.
  - Runs profiling and high-load tests.
  - Optionally hosts Linux network namespaces in a later milestone.

Linux laptop
  - Runs traffic generator A.
  - Captures received virtual frames and validates ordering/loss.
  - Runs tcpdump/Wireshark for the UDP lab transport when useful.

Windows laptop 1
  - Runs Python control client.
  - Applies topology and route updates.
  - Collects counters and state snapshots.

Windows laptop 2
  - Runs traffic generator B.
  - Injects malformed traffic, disconnects, and delayed/reordered updates.
  - Confirms Windows portability.

Safety and practicality:

- Begin on a trusted private LAN.
- Bind control and data sockets only to explicitly configured interfaces.
- Do not expose the lab control service to the public internet.
- Use non-privileged UDP ports.
- Add authentication before any non-lab deployment.
- Keep the deterministic single-machine mode as the primary correctness test.

6. TEST STRATEGY
================

Unit tests:
- address/prefix boundaries
- valid and malformed packet parsing
- MAC learning and aging
- LPM overlap and default route
- queue boundaries and shutdown
- serialization round trips

Integration tests:
- two-host same-VLAN forwarding
- inter-VLAN routing
- ACL permit/drop/count
- unresolved neighbor then resolution
- route replacement while traffic flows
- state drift followed by reconciliation

Fault-injection tests:
- fail before and after each table operation
- full MAC, route, ACL, and queue resources
- corrupt or truncated packet
- duplicate/out-of-order control operation
- endpoint loss and restart
- process restart with stale observed state

Concurrency tests:
- multiple producers and consumers
- concurrent route updates and reads
- shutdown under full and empty queues
- repeated stress under ThreadSanitizer

Performance tests:
- packets per second
- forwarding latency distribution
- route updates per second
- lookup latency versus route-table size
- queue contention versus worker count
- allocation count and memory footprint


7. INTERVIEW STORY OUTPUTS
==========================

By the end of the project, prepare these evidence-backed stories:

1. Requirements-to-release story:
   Trace one feature from requirement and design through tests and deployment.

2. Difficult C++ bug:
   Use a real parser, lifetime, invalidation, or concurrency defect found here.

3. Performance optimization:
   Present profiler evidence and before/after benchmark results.

4. Hardware/software mismatch:
   Use an injected desired/observed state divergence and reconciliation.

5. Resource exhaustion:
   Explain table-full or queue-full behavior and why it is safe.

6. Cross-functional design:
   Explain the contract between control plane, hardware interface, and data plane.

7. Failed approach:
   Document an idea that measurements or testing disproved.

8. Portability:
   Explain a Linux/Windows difference and how the interface isolated it.


8. DEFINITION OF DONE
=====================

The complete project is done when:

- It builds and runs on Linux and Windows from documented commands.
- One process can run deterministic end-to-end L2 and L3 scenarios.
- Four machines can exchange virtual frames through configured UDP ports.
- Tables and queues enforce configurable resource limits.
- Desired/observed state drift can be injected, detected, and repaired.
- Unit, integration, fault, concurrency, and performance tests are repeatable.
- Results include counters, traces, and machine-readable reports.
- At least one optimization has credible before/after evidence.
- Documentation explains architecture, decisions, limitations, and operations.
- You can answer the milestone questions without memorized scripts because you
  implemented and measured the relevant behavior.


9. FIRST IMPLEMENTATION SESSION
===============================

Build M0 and M1:

1. Create standalone CMake targets: library, CLI, and tests.
2. Add strict compiler warnings.
3. Implement MacAddress, Ipv4Address, and Ipv4Prefix.
4. Test parsing, formatting, prefix normalization, and matching.
5. Add byte-order helpers and explain every conversion.
6. Implement safe Ethernet parsing without unsafe buffer casts.
7. Run tests on one Windows and one Linux computer.

Questions you should be able to answer after this session:

- What owns every object?
- Which operations can fail, and how is failure represented?
- What is undefined behavior in a naive packet parser?
- What changes between host and network byte order?
- Why is a value type useful for an address?
- Which tests establish that malformed input is safe?
